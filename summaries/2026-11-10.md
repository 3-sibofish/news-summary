**Strengthening our defenses against distillation attacks**

**核心论点**：Anthropic 详细披露其反蒸馏防御体系，称已将数据窃取率降低 90-99%。

**关键要点**：
- 蒸馏攻击定义：通过欺诈账号网络大规模提取模型响应以训练竞争模型，通常无需成比例的安全防护
- **具体案例**：Zhipu 蒸馏 Claude Fable 5 开发 GLM-5.3（因 Fable 5 网络防护太强而转向旧版 Claude 和他家模型）；CAISSI 评估 GLM-5.3 为迄今网络安全能力最强的开放权重模型，但其防护易被绕过
- **国家安全案例**：Moonshot 的 Kimi 模型 secretly forwarding 请求至 Claude，其中包含 PLA 关联用户分析特定个人 CCTV 监控的请求
- 三阶段防御：控制 reasoning 流向（preserved thinking 阻止跨会话/跨账号/跨模型提取）、双层分类器系统拦截提取尝试、主动 patch 已知攻击模式
- 代价：拒绝蒸馏者带来的"有意义收入"和万亿级 token 付费流量；合法用户需更新集成
- 早期措施（reasoning 摘要）使蒸馏效果从 80.4% 降至 71.8%，但攻击者转向主动提取（如 12,000 种不同 trick 请求）

**值不值得深读**：非常值得。这是行业最详细的反蒸馏技术披露，包含具体攻击者身份、技术手段和地缘政治影响。

**Control Room: A central system to track and stop model workloads across our research infrastructure**

**核心论点**：OpenAI 构建中央控制系统，可在安全或安保问题出现时 35 秒内停止任意研究推理工作负载。

**关键要点**：
- 覆盖所有研究推理负载：RL 训练、评估、agentic sampling、数据处理等
- 与 misalignment monitoring 系统集成，monitor 模型检测异常后可直接触发停止
- 架构：workload 申请 job_id → inference engine 每次请求前向 Control Room 查询授权 → 已终止 job 被拒绝
- **fail-closed 设计**：Control Room 自身故障时，所有推理请求自动被拒绝
- 35 秒延迟来自推理授权缓存层，正努力降至零
- 关键设计哲学：workload 代码多变不可靠，安全机制实现在更集中统一的 inference 层
- 持续进行 agentic 和程序化扫描，防止用户意外或恶意启动绕过 Control Room 的 rogue engine

**值不值得深读**：值得。这是了解 frontier lab 内部安全架构的罕见技术披露，尤其对"fail-closed"设计和 monitor→stop 链条有详细说明。

https://openai.com/index/control-room

- 与 REAP 一阶方法有强关联：F 矩阵对角线几乎完美恢复 REAP 评分（Spearman ρ≈0.99），所有改进来自二阶交互项
- 在 Qwen3.5-122B/35B 和 GLM-4.5-Air 上测试，平均排名 2.07/5，top-1 率 39%，top-2 率 67%

**Uber's AI infra, from the inside**

**核心论点**：深度披露 Uber 内部 20+ 开发工具及其向 AI agent 时代的演进，由 Distinguished Engineer Uday Kiran Medisetty 主讲。

**关键要点**：
- 服务数量剧烈波动：2015 年 2 个 → 2019 年数千个 → 2026 年与 2019 年相近但业务规模 10 倍
- 大量自研工具因 off-the-shelf 软件无法处理规模或根本不存在：uOwn（服务所有权）、M3DB（5 亿指标/秒，后开源为 Chronosphere 基础）、Cadence（多日期工作流引擎，Temporal 基础）、Morpheus（支持双边/三边市场的 feature flag + 实验系统）
- **城市作为一等概念**：贯穿可观测性、feature flag、部署、服务分片到底层基础设施；早期数据库按城市分片，现今每个城市固定云区域可随时故障转移
- **Model Gateway（2023）**：所有 AI 建设必须模型和 harness 无关，支持 Anthropic、OpenAI、自托管开源模型；扩展出 AI Guard（安全中间件）、支出追踪、审计日志
- **AIFX**：harness 包装器，切换 harness 时保留所有设置、skills、plugins；当前支持 Claude Code、Codex、OpenCode
- **混合 AI 支出模式**：工程师获分配支出层级，超限后经理审批即可继续；CostCheck 插件跨会话提供成本优化建议；近月 token 成本降低约 50%
- **代码审查瓶颈**：所有 PR 仍需人工审查，但 AI 预审查、截图/视频自动附加、风险评分辅助决策
- **CI "code red"**：12 个月内 CI 任务翻倍，将简单任务（lint、build、template 规则）移至"内循环"由 agent 在提 PR 前通过 `afx validate` 执行
- **PR 分类追踪**：按 feature/bugfix/maintenance/testing/docs 分类，观察到 feature PR 占比上升、maintenance 下降
- **工程师角色演变**："工作是构建 agent 产生可靠输出的正确上下文"——context engineering、多任务处理、审查验证能力变得至关重要

**值不值得深读**：非常值得。大型科技公司内部 AI 基础设施的最详细公开披露之一，包含具体系统名称、决策逻辑和量化数据。

**Faster Fourier Transforms**

Recht 拆解 OpenAI 数学论文库中声称的"更快 FFT"。发现其复杂度为 O(n log n / log log n)，但隐藏常数 C 估计为 10^100（当 N=10^12），属于"星系级算法"（galactic algorithm）——即理论上渐近更优但实际宇宙原子总数级别的输入规模才显现优势。更根本的问题：该"算法"假设可在单步操作中精确乘任意精度复数，所需内存随 n 超多项式增长，与实际计算机完全脱节。Recht 追溯历史：1973 年 Morgenstern 证明有界系数下 FFT 下限为 ½ n log n；2014 年 Ailon 证明无严重数值不稳定则无法突破 n log n——OpenAI 的结果实为计算机科学家未能正确定义"计算"的形式化规格。

https://www.argmin.net/p/faster-fourier-transforms
